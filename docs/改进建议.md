主要风险与改进建议
1. 默认部署配置仍偏 Demo，不适合直接作为生产基线
docker-compose.yml 中存在固定的 MySQL root 密码 workbench，生产覆盖配置中还直接写入公网 IP。虽然 JWT 和 AI Key 使用了外部文件，但数据库密码、HTTPS、域名、TLS 和密钥轮换仍需要进一步治理。
建议：
◦ 所有密码均从 Secret 或环境变量注入
◦ 禁止生产容器暴露 MySQL、Java、Python 端口到公网
◦ 使用 HTTPS 和域名
◦ 增加非 root 数据库用户
◦ 将公网 IP、镜像地址等配置完全参数化
2. 存储层存在单机化瓶颈
上传文件和 Chroma 都依赖本地 Docker volume。对于单台 ECS Demo 没问题，但不利于：
◦ 多实例扩展
◦ 跨机器迁移
◦ 灾备
◦ 大规模素材管理
◦ 向量库高可用
生产演进可以考虑对象存储、独立向量数据库或更明确的备份恢复策略。
3. AI 依赖较重，启动和镜像体积可能较大
requirements.txt 包含 torch、sentence-transformers、chromadb和 reranker 相关依赖，AI 镜像可能较大，项目也已经在部署文档中记录了镜像拉取超时问题。
建议：
◦ 区分 CPU/GPU 和开发/生产依赖
◦ 使用更明确的模型缓存策略
◦ 将 Embedding/Rerank 服务独立化或按需加载
◦ 增加模型下载、缓存和健康检查指标
4. 测试覆盖不均衡
Python 侧已有文档解析、语义切分、混合检索和 source anchor 测试，这是亮点；但从仓库结构和脚本配置看，Java 与前端的自动化测试证据相对少，CI 也更偏编译/构建验证。
建议补充：
◦ Java Controller、Service、权限和 SSE 集成测试
◦ RAG 端到端评估集与 Recall@K、MRR、引用准确率指标
◦ 前端核心流程测试：登录、上传、Chat 流式、Campaign 保存
◦ CI 中强制执行测试、Lint、镜像构建和安全扫描
5. 可观测性仍可加强
已有 ai_call_log、Token 用量和管理员统计，但还缺少完整的：
◦ 结构化日志
◦ Trace ID
◦ 请求耗时
◦ 模型失败率
◦ RAG 命中率
◦ SSE 中断率
◦ Prometheus/Grafana 等监控
如果后续面向真实团队使用，这会是重要补强方向。
6. 文档管理成本偏高
文档内容很丰富，但 deploy.md 已经非常长，混合了安装说明、历史踩坑、CD 细节和运维手册。建议拆分为：
◦ 本地开发
◦ Docker 部署
◦ ECS 生产部署
◦ 故障排查
◦ RAG 评估
◦ 运维与备份
这样新用户更容易找到最短路径。

如果目标是作品集、面试展示或内部业务验证，目前已经很有说服力；如果目标是对外提供稳定的生产 SaaS，下一阶段应优先处理密钥与网络安全、数据备份、测试覆盖、监控告警和存储解耦。
